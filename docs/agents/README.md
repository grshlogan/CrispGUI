1. A004 builds a delivery when a task packet asks for it, from a clean tree at a commit that has been pushed to `origin`; A003 records it in the table above and gives the owner the steps.

A `BUILD-INFO.txt` inside the folder names the commit, the build type, and the toolchain versions. A diagnostic delivery, `crispgui-diag-<tool>-<short SHA>.zip` from `tools/package-diagnostic.sh`, carries one measurement tool of `tools/diagnostics/`, its `BUILD-INFO.txt`, and, from P4-T3 on, `WINDOWS-AGENT.md`. The Phase 0 smoke deliveries of `tools/smoke/package-eui-smoke.sh` carry neither a checklist nor the brief. The Windows side does no development and needs no source, so a Git bundle or a `git archive` snapshot is made only on request.
3. Deliveries go to `<HANDOFF_OUT>`, a directory outside the checkout; the proposed location is `/home/claude/projects/CrispGUI-handoff/outgoing/`. The owner copies the folder to Windows by hand or with a copy script.
4. Each application delivery carries `CHECKLIST.md`, the numbered Windows checks of its phase (`tools/windows/CHECKLIST.md`), each with its steps, the expected result, and what to send back; the owner or the Windows-side agent runs them. A diagnostic delivery has no checklist: the owner's task says how to run it. From [P4-T3](tasks/P4-T3-delivery/packet-v2.md) on, application and diagnostic deliveries also carry `WINDOWS-AGENT.md`, the brief for that agent (`tools/windows/WINDOWS-AGENT.md`).
5. Windows results come back through the owner, per check and with the files the check names (message, log excerpt, screenshot, or files). The Windows-side agent collects them in `results\<UTC time>\` inside the delivery folder, which the owner copies back into that delivery's folder in `<HANDOFF_OUT>`. They are recorded against the delivered SHA and the platform; a phase closes on Windows only with `test-results.txt` in hand.
6. Nothing reads or writes across the system boundary, and WSL2 never mounts Windows drives.

### Decisions

- No coding subagents by default. A004 implements each packet itself, in one worktree. Coding subagents in worktrees of their own, which the Skill allows, do not pay off at this project's size: the phases are sequential and build on each other; most tasks touch shared files such as `CMakeLists.txt` and `tests/CMakeLists.txt`, so parallel branches would conflict; every worktree needs its own two clean builds with EUI-NEO; each fresh subagent first re-reads the project rules, which costs more than it saves on blocks of a few hundred lines; and the bottleneck is the Windows round trip, not coding speed. A packet may mark blocks as parallel-safe (disjoint write scopes, no shared build files); only then may A004 hand them to coding subagents, each in its own worktree.
- An independent Review for every code task. Phase 4 showed why: the Windows run and the mutation checks caught defects that the coding pass had missed. Each round is one fresh session that never sees the coding conversation. Profiles: `standard` for ordinary code; `strict`, which adds the packet's mutation matrix, for persistence, concurrency, the HTTP transport, and process control. Documentation changes by A003 go without a Review, as in the owner's Chronicle Harbor practice.
- Candidates are commits. A round's candidate is a commit on the task branch: commits are immutable and hold every tracked input, and the owner's fonts, ignored by Git, are the only input outside them. This replaces the Skill's snapshot bundles; the reviewer exports the commit with `git archive` into a directory of its own.
- Review sessions, by the owner's direction of 2026-10-14: the Review runs as the Skill's Claude Code CLI profile has it, a fresh top-level session that the owner starts. From round 13 to 23 A004 dispatched a fresh subagent with A003's fixed prompt instead, to keep the cost low; three such dispatches (P5-T3 R01 once, P5-T4 R01 twice) died on the account's five-hour limit (HTTP 429) and lost all their work, whereas a top-level session can continue after the limit resets. A review session has no identity of its own: its name, `<task-id> <Rxx> Review` (for example `P5-T4 R01 Review`), and its model go into its report. It runs in `<REVIEW_ROOT>`, an empty directory outside both checkouts, so that it neither loads nor writes the project's Claude Code memory and touches `<CODING_ROOT>` only to read the candidate and write its report.

### Task flow

1. A003 writes `docs/agents/tasks/<task-id>/packet.md` ([format](tasks/README.md)), pushes it, and notifies A004.
2. A004 fetches, creates `a004/<task-id>` from `origin/main`, writes `receipt.md` (state `Coding`), implements, runs the packet's gates, and commits the candidate.
3. A004 writes the filled Review prompt to a file and gives the owner the launch command of [tasks/README.md](tasks/README.md#review-dispatch); the owner starts the review session. The reviewer writes `review-R01.md`; once the owner says that session has ended, A004 commits the report unchanged, together with the updated receipt.
4. On FAIL, A004 answers each finding in the receipt (AGREE with a fix and a check that catches the defect, or DISAGREE with evidence), commits the repair, and has the owner start `R02` in a new review session. After `R03` without a PASS, or on a question of scope or contract, A004 stops and asks A003.
5. On PASS: if `origin/main` moved, A004 rebases the task branch onto it and reruns the gates when code changed underneath; then `git push origin HEAD:main`, fast-forward only. The receipt records the reviewed commit; A003 records the merged one.
6. A004 notifies A003, which checks the receipt and the report against the candidate, updates the [task index](tasks/README.md#task-index), and records the results in the phase report and STATUS.

Deliveries are tasks too: A004 builds and packages them; A003 records them, changes `CHECKLIST.md` where no task does, and relays the Windows results.

### Communication

Files are the record: packets, receipts, Review reports, this register, and the phase reports. A003 and A004 run on the same WSL2 host, so Claude Code's own session messages may carry pointers between them (task ID, commit, file path) at four points: a packet is ready, a task is merged, a decision is needed, a delivery is built. Session messaging works in both directions on Claude Code 2.1.294 with both sessions in bypass mode (`observed`): A003's notice reached A004 in round 15, and A004's notice that P4-T1 was merged reached A003 in round 16. The session names are `A003[ClaudeCode]DocArch Planner` and `A004[ClaudeCode]Master`. The list also shows `A001[ClaudeCode]DocArch Planner`, a session of another project, so messages go to the exact names above. When a message does not arrive, the owner relays the pointer. A message never grants authority or replaces a file. The owner runs the sessions in bypass permission mode (round 13); that mode removes prompts, not rules: write scopes, protected paths, and the Review stay in force.

### Token budget

A003 reads receipts and reports rather than diffs, unless a report raises a question. Packets stay small: one coherent change, usually a few hundred lines. Reviewers report findings and evidence, not summaries of the code. Helpers get precise, self-contained instructions.

Installed Skills: `agent-dev-loop`, used as above, and `reference-audit` (`~/.claude/skills/codequality/reference-audit/`), for independent audits of external projects, advisory only. A Skill file being present does not put it in a session's context; a task names it and the session reads it.
