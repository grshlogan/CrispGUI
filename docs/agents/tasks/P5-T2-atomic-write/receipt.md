Behavior, in the order of `WriteFileAtomically` (`src/platform/files.cpp:100`): pick a temporary name `<start of the name>.<16 hexadecimal digits>.tmp` in the destination's directory that does not exist (up to eight tries; the start of the name is the destination's name cut to 40 units at a character boundary, so the temporary name is at most 61 units long); create it (`OpenFileForWriting`); write the bytes; flush them to the disk; close it; `RenameOverFile` it over the destination. Any failure removes the temporary file, leaves an existing destination as it was, and returns false with a message that names the step and the system's reason: "Could not create the temporary file …", "… write …", "… flush … to the disk", "… close …", or "Could not replace <destination> with the temporary file …".

Decisions inside the packet's freedom:

- The packet's building blocks are named `AtomicTemporaryPath` and `WriteFileAtomically` as it suggests. The replace step is `RenameOverFile`, not `ReplaceFile`: `<windows.h>` defines `ReplaceFile` as a macro (`ReplaceFileA`), so the first MinGW build of the candidate (G4) failed in the test and the Windows implementation would have defined a different function than the header declared. The header says why.
- The temporary file's name keeps the start of the destination's name and ends in `.tmp`, so a file left by a crash is recognizable. Review R01 F1 showed that adding 21 units to a destination name close to the limit of 255 bytes made the atomic write fail where a plain write succeeds; the kept start is therefore bounded. The temporary file is in the destination's directory and never in the system's temporary folder.
- No directory is flushed after the rename; the packet asks for the file's flush only, and the durability of the rename itself is the file system's. The mode and owner of an existing destination are not carried over, and a symbolic link at the destination is replaced by a regular file: the new file has the default mode of `fopen` (`0666` and the umask on POSIX). The header says so (Review R01 F4).
- The function holds no global state apart from the atomic counter of the name generator, so concurrent calls, even for the same destination, each write their own temporary file; the last replacement wins.
- `std::filesystem::exists`, `remove`, and `directory_iterator` are used through their `std::error_code` overloads, as the project's conventions ask (no exceptions).

- The writer has no caller yet: the SRT output of the Transcribe page and Phase 7's job files will call `WriteFileAtomically`.
- A temporary file left by a crash stays until someone removes it; its name (`<name>.<digits>.tmp`) says what it belongs to. Nothing sweeps them in this task.
- Not preserved on an existing destination: its mode, owner, and extended attributes (the new file is created with the defaults).
